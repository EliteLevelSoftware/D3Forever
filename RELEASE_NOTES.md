## Fixed: the retail client rejected storages built by 1.4.3

Installing 2.7.6 with v1.4.3 produced a storage the client refused to open
(`GetKeyMapping failed during Validation` ? `E_STORAGE_INIT`), and even after that was
past it failed with `Data Retrieval Error` / `Data Error`. Three independent defects in the
CASC writer plus a missing NGDP catalog repair were responsible.

### 1. `.idx` bucket placement for the 16 archive header records
Every `data.NNN` starts with 16 cross-link header records at offsets 0..479.
Blizzard stores the record at offset `30*j` in bucket `j`, i.e. one bucket *above* the
bucket its key hashes to. The rebuild path used the plain hash, so every header record
landed one bucket early and the client could not build its key mapping.

### 2. Duplicate keys
When the same EKey exists in more than one archive, the client's own writer keeps the
**last** occurrence. The rebuild path kept the first, so a handful of entries pointed at a
different (still valid, but different) copy than the client expected.

### 3. `.idx` file size
The client expects `ceil((40 + entries) / 4096) * 4096 + 32 KB`; the previous code padded to
a 64 KB boundary and produced shorter files, which the client silently discarded.
Index files generated by 1.4.4 are now **byte-identical** to the ones Blizzard ships.

**Verified** by rebuilding the storage of a working retail 2.7.5 install (all 16 `.idx`
files byte-for-byte identical to the original) and by cold-starting the 2.7.6 client.

### 4. New `NgdpConsistency` pass � the client�s CDN catalog
The client resolves data through `Data/config` + `Data/indices`, not only through the local
storage. Blizzard has retired several artefacts that old builds still reference, so a
storage assembled from live CDN data has a catalog full of dead links:

- archives whose `.index` returns 404 are now removed from `archives` /
  `patch-archives` (and from the matching `*-index-size` lists);
- the derived `archive-group` / `patch-archive-group` files are regenerated from the
  surviving archives and written under the MD5 of their own footer, exactly like the
  retail client names them;
- the CDN config is rewritten and re-keyed (NGDP names configs after their own MD5) and
  `.build.info` is pointed at the new key;
- stale `Data/data/*.mrk` repair markers are removed.

This runs automatically at the end of every installation and can be re-applied to an
existing install with the new CLI flag:

```
Diablo3Forever.exe --fix-ngdp "C:\Games\DiabloIII-2.7.6.91007"
```

`--rebuild-casc <root>` now also runs the catalog repair, so repairing a storage fixes both
halves in one command.

### 5. New `--verify-casc` — offline completeness report

```
Diablo3Forever.exe --verify-casc "C:\Games\DiabloIII-2.7.6.91007"
```

Reads the build's download manifest (from the local storage when Blizzard no longer serves
it) and checks every chunk the client can request against the local `.idx` files:

```
Storage records      : 274,876
Chunks required (enUS): 274,616
[OK] CASC storage is COMPLETE: every chunk the client can request is present.
```

Missing chunks are listed with their keys and total size, so a gap can be diagnosed without
launching the game. The check is locale-aware: an install built for `enUS` that is later
switched to another language will correctly report the missing text/audio chunks.

---

## Notes on retired content
Blizzard permanently deleted some year-old artefacts from the CDN. `D3Forever` drops them
from the catalog instead of failing, which is what makes 2.7.6 launchable today; the game
data itself is complete because those chunks are fetched as loose files.

# Diablo 3 Forever v1.4.3 — Security Hardening

**Release Date:** November 12, 2026  
**Build:** `v1.4.3` (source build)  
**Binary:** `Diablo3Forever.exe` (Windows x64 Single-File Standalone — Zero Dependencies)

---

## 🔒 Security Review & Hardening

### 1. HTTPS Everywhere (no more plaintext downloads)
- All Blizzard endpoints are now contacted exclusively over **HTTPS**:
  - NGDP patch/version endpoints (`us`/`eu`.patch.battle.net, `.version.battle.net`) — previously plain HTTP on port 1119.
  - All CDN content (`config`, `data/*.index`, archive chunks) — the downloader previously hard-coded `http://`.
  - Legacy `.direct` MPQ mirrors now use `https://blzddist1-a.akamaihd.net` instead of `http://dist.blizzard.com.edgesuite.net` (whose TLS certificate does not match its hostname).
  - Generated `.build.info` server lists and every catalog `CdnConfigUrl`/`CheckUrl` are HTTPS.
- Plaintext HTTP meant any network attacker (public Wi-Fi, malicious proxy, ISP) could swap the requested executable/DLL bytes for a trojan. That channel is now closed.

### 2. CDN Host Allow-Listing
- Host names returned by the CDN metadata response are only used when they resolve to a Blizzard-controlled domain (`.blizzard.com`, `.battle.net`, `.akamaihd.net`, `.edgesuite.net`, `.llnwd.net`) **and** parse as a valid DNS name.
- Prevents a tampered/spoofed CDN descriptor from redirecting downloads to an arbitrary third-party host.

### 3. Path-Traversal Protection
- Every file path that originates from remote metadata (install manifest names, MPQ list files, `.mfil` entries, `delete.lst`/`patch.lst` lines, mirror layout) is resolved through `SafePathUnder()` and rejected if it would escape the target directory.
- A malicious manifest can no longer write outside the install folder or delete arbitrary files on disk.

### 4. Self-Updater Integrity Verification
- The updater now downloads `SHA256SUMS.txt` from the same GitHub release and verifies the **SHA-256** of `Diablo3Forever.exe` before executing it; a mismatch aborts the update and deletes the download.
- Update URLs must be `https://github.com` (or `*.githubusercontent.com`).
- Paths embedded into the updater batch file are validated, preventing batch/metacharacter injection through the executable or temp folder path.
- The `-ExecutionPolicy Bypass` flag was removed from the inline PowerShell post-install helper.

### 5. Download & Decompression Integrity
- `BuildConfig`, `CDNConfig` and `ProductConfig` files are verified against their MD5 content hashes (and a corrupted local cache entry is discarded and re-fetched).
- Every BLTE chunk is validated against the per-chunk MD5 stored in its BLTE header, and decoded lengths must match the manifest, so truncated or corrupted payloads are rejected instead of being written to disk.
- Legacy MPQ binary diffs (`PTCH`/BSD0) now enforce the post-patch MD5 from the patch stream (previously computed but not compared), and resumed MPQ downloads verify the expected size.
- Input validation added for config/index hashes, `--locale` and `--region` values (they are interpolated into generated scripts/config files).

### 6. Historical CASC Resilience (fixes build 2.7.6 and friends)
- **Retired archive indices no longer abort the install.** Blizzard deleted a handful of per-build archive indices (e.g. 8 of the 126 for `2.7.6.91007`); these are now logged as `[Notice]` and skipped instead of failing the whole pipeline.
- **Live shared archive federation is now always applied.** Historical `CDNConfig` files only list the archives that existed at release time, so chunks such as the `root` manifest were unreachable. The engine now merges the build's catalog with the live shared catalog (up to 255 archives), which restored `2.7.6` (its `root` chunk lives in the live archive `6ab01a8e…`).
- **Chunk/range hardening:** partial range responses are rejected and validated against the requested byte range, so an incomplete CDN response can no longer write truncated data.

### Unchanged
- No behaviour, UI, catalog or build-pipeline changes. Verified with live CDN installs (CASC 2.8.0 dry-run and legacy MPQ 1.0.8a) and the GUI.

- **The Discovery:** Exhaustive edge-node network inspection revealed that Blizzard **never purged the standalone executables or libraries** for Patch 2.7.4.84161 from their live CDN edge nodes!
- **Zero Third-Party Downloads Needed:** `Diablo III64.exe` (CKey `A38867FA...`), `Diablo III.exe` (CKey `B1609FC2...`), `battle.net.dll`, `libcef.dll`, and `icudtl.dat` stream **live directly from Blizzard's NGDP CDN servers**!
- **Cryptographic Bit-for-Bit Validation:** Every extracted binary is verified against Blizzard's official MD5 Content Key (CKey), ensuring 100% genuine Blizzard binaries.
- **Server Standard Ready:** Patch 2.7.4 is the global community standard for Diablo III private server emulators (such as DiIiS) and is now instantly installable with a single click.

### 2. Historical CASC Rescue Engine (2018 – 2024 Builds)
- **Reconstructed NGDP Manifest Catalog:** Added verified live Blizzard `BuildConfig` and `CDNConfig` manifests for historical CASC eras previously thought lost:
  - `2.6.4.55430` (Season of Grandeur)
  - `2.6.9.68722` (Trials of Tempests)
  - `2.6.10.71254` (Shadow Clones)
  - `2.7.3.82785` (Echoing Nightmare)
  - `2.7.4.84161` (Angelic Crucibles)
  - `2.7.6.91007` (Solo Self-Found / Visions of Enmity)
  - `2.7.7.92326` & `2.7.7.93903` (Rites of Sanctuary & Visions Permanent)
  - `2.7.8.97927` (Maintenance / Mac 64-bit)
- **Shared Archive Asset Federation:** Automatically leverages the 17.37 GB of shared textures, sound banks, and world data hosted across Blizzard's 150 active CDN archive blobs.

### 3. Option B Clean Binary Package System
- **Rock-Solid Binary Recovery:** Instead of fragile 2–4 MB binary diffs that break whenever retail patches update, Diablo 3 Forever adopts the Option B Clean Binary Package system.
- **Multi-Tiered Asset Recovery:**
  1. Primary: Direct live download of loose files from Blizzard NGDP CDN.
  2. Secondary: Detection of local clean binary zip archives (`d3-{build}-binaries.zip`) in offline archive caches or application cache.
  3. Tertiary: Optional automated streaming from community binary delta mirrors (`BinaryDeltaUrl`).
  4. Quaternary: Rescue of verified shared runtime libraries from existing local Diablo III installations.
- **Zero-Dependency Native Unpacking:** Employs .NET's built-in `System.IO.Compression.ZipFile` for instant decompression in ~1 second.

### 4. UI & Dossier Upgrades
- **Live CDN Ready Badges:** Historical CASC versions with live Blizzard manifests now display live green indicators in the version selector drawer without prompting for mandatory offline archives.
- **CASC Provenance in Dossier:** Right-clicking any CASC build in the drawer displays its exact Blizzard `BuildConfig` and `CDNConfig` hashes and CDN endpoints in the Historical Dossier modal.
